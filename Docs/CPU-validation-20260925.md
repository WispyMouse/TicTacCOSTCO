# TicTacCOSTCO CPU: implementation and validation

A first CPU implementation was prepared on branch `feature/budgeted-cascade-cpu`, based on [upstream commit 475c0b61c797f277ef993360b39c5c9d9bee271a](https://github.com/WispyMouse/TicTacCOSTCO/commit/475c0b61c797f277ef993360b39c5c9d9bee271a). The implementation, tests, and this report were chiefly generated by Perplexity Computer, an AI assistant, at the direction of `rmc3`, not personally written by that submitting account.

This report records the pre-publication validation run; implementation and verification were performed directly, without pplx-reflect delegation or writes to the user's local device. See `Docs/AI-PROVENANCE.md` for code provenance and the distinction between AI generation, human direction, and account-based submission.

## Delivered

- **Rules-aware CPU:** A detached state model, cascade-aware evaluation, reward-vector MCTS for 2–6 players, and full-width alpha-beta for small positions with two survivors.
- **Scalable settings:** Easy/Normal/Hard work presets, one smooth board/player-size adjustment, independent style controls, and separate work, node, wall-time, and frame-slice limits.
- **Unity integration:** A new `AISearchCore` asset selected in the game scene, resumable main-thread search, reset/disable cancellation, stale-result checks, and completed-search diagnostics.
- **Regression protection:** Original rule tests retained, differential tests against actual `GameState`, independent tiny-position minimax, and control-flow smoke tests.
- **Developer workflow:** A .NET Standard compatibility build, a .NET 8 headless test runner, exploratory leagues/benchmarks, and `Docs/CPU.md`.

The sample scene retains its existing all-human seat default. To play against the new CPU, set `TurnOrderHolder.InitialComputerPlayers` to `[1]` for the second seat; difficulty and budgets live in `AICore_Search.asset`. No new player-facing settings UI is claimed.

## Verification performed

The production rules/search sources build as .NET Standard 2.1 with **zero warnings and zero errors**. The final regression run passed **60 tests**, with four explicitly marked experiments excluded from that default run; all four experiments were then run separately and completed successfully.

The checks include:

- Twelve seeded games for each of five size/player combinations spanning 3×3 to 20×20 and 2–6 players. Every hypothetical score for every player at each tested position, and every actual transition, is compared with the game's original rules implementation.
- Forty small two-player positions checked against exhaustive minimax built by replaying the original `GameState`, not the new search model.
- Four-axis scoring, consumed-line history, rectangular/custom-length inputs, terminal ordering, eliminated players, legal fallback, snapshots, work/node bounds, and frame-slice reproducibility.
- Headless control-flow checks for reset, state-version changes, human toggles, replacement game objects, disable/unsubscribe, consecutive CPU turns, and old-core compatibility.

The console tests use narrowly scoped Unity API shims to compile the existing AI bodies and adapter loop. Those checks do not validate actual Unity serialization, rendering, frame scheduling, or Unity RNG behavior.

## Exploratory strength results

The Normal preset won all **128 two-player games** in this initial league against the existing random, survival-only, Investor, and MayAttack algorithm bodies. Each opponent/board combination used eight paired seeds with both CPU seats, on 5×5 and 8×8 boards; MayAttack used the scene asset's 0.05 / 1 / 1 attack probabilities.

This is an encouraging baseline, not a general-strength guarantee. The league is small, uses a seeded headless RNG shim for legacy bots, has no human opponents, and does not establish Android behavior or performance on 20×20 matches.

The multi-player results against MayAttack opponents were:

| Board | Players | CPU wins | CPU losses | Game-level draws |
|---|---:|---:|---:|---:|
| 5×5 | 3 | 12 | 0 | 0 |
| 8×8 | 3 | 11 | 1 | 0 |
| 5×5 | 6 | 2 | 1 | 9 |
| 8×8 | 6 | 4 | 8 | 0 |

Each row contains twelve games with varied first mover and CPU seat. A reported draw describes the game's terminal result, not necessarily an equal reward for every original player; the search itself gives draw utility only to still-active players.

Adjacent difficulty presets produced these preliminary results, from the higher preset's perspective:

| Board | Matchup | Wins | Losses | Draws |
|---|---|---:|---:|---:|
| 5×5 | Normal versus Easy | 14 | 2 | 0 |
| 5×5 | Hard versus Normal | 9 | 7 | 0 |
| 8×8 | Normal versus Easy | 10 | 6 | 0 |
| 8×8 | Hard versus Normal | 11 | 5 | 0 |

The observed ordering is encouraging but not sufficiently established to call the presets calibrated skill levels. In particular, the 9–7 result is weak evidence, not a decisive strength improvement.

## Performance evidence and its limits

A warmed desktop smoke benchmark completed all 45 combinations of five board sizes, three player counts, and three presets. The raw experiment results record work units, simulations, nodes, elapsed time, allocations, and selected moves for an empty-board position in each combination.

This is not a mobile benchmark, a sustained thermal test, a worst-case bound, or a measurement of Unity frame stalls. Allocations are cumulative per search, not peak retained memory; the node cap is not a strict byte quota, and frame limits are checked between operations rather than enforced by real-time preemption.

## Apply the patch

Apply it to a clean checkout of the pinned upstream revision, not blindly to a later revision:

```sh
git switch -c feature/budgeted-cascade-cpu 475c0b61c797f277ef993360b39c5c9d9bee271a
git apply --check /path/to/tictaccostco-cpu.patch
git apply /path/to/tictaccostco-cpu.patch
dotnet build Tools/HeadlessTests/CoreCompatibility.csproj -c Release
dotnet run --project Tools/HeadlessTests/HeadlessTests.csproj -c Release -- --workers=0
```

The patch includes source, Unity metadata/asset wiring, tests, and documentation. The validation XML files preserve the local runs separately; generated binaries and NuGet caches are not part of the patch.
